# Overview

How the app fits together, and the decisions and rules that aren't obvious from the code. What's missing or broken is in the [issues](https://github.com/nindalf/CaptainsLog/issues), not here.

## Shape

- **CaptainsLogKit** (`Sources/CaptainsLogKit/`): models, store, sync, and every rule the app and CLI share. No UI frameworks.
- **App** (`captainslog/captainslog/`): SwiftUI, unsandboxed, single user.
- **CLI** (`Sources/captains-log/`): how Claude reaches the store. See `docs/cli.md`.
- **Skills** (`skills/`): `captains-log` (answer from the store), `weekly-review` (Friday interview into brag-doc entries) and `meeting-prep` (prep notes for an upcoming meeting; an upcoming meeting's page shows its command until a notes field is opened). Homebrew links them into `~/.claude/skills` and Codex's `~/.agents/skills` (`captains-log skills install`); `just install-skills` links a checkout's. `weekly-review/agents/openai.yaml` keeps Codex from running it unasked.
- **Store:** one SwiftData SQLite file (WAL) at `~/Library/Application Support/CaptainsLog/`, shared by app and CLI. `CAPTAINSLOG_STORE_DIR` points either at a scratch store, which never syncs. Versioned schema with a migration plan (`Schema.swift`); see the schema-change rules in CLAUDE.md. Expected scale after a year: a few thousand records per type, so query tuning doesn't matter.

## Conventions across the app

- **Dates** go through `DateLabel` (Kit): Yesterday/Today/Tomorrow, a weekday within this Monday-to-Sunday week, else "21 Oct", with the year only outside this year. Dates of things already done are picked with `DayField`.
- **Detail pages** (meeting, interview, person) are documents, not `Form`s (`DetailPage`): an editable title, a metadata line, boxed `DetailSection`s. A project's header uses the same `DetailHeader`.
- **Content width:** lists and detail pages share one centred 760pt column (`contentColumn()`, inside the `ScrollView` so the scroller stays at the edge). Calendar and Dashboard fill the window. Todos keeps its list column (`SmartListColumn`), styled as a second level of the sidebar, its rows as tall, its icons as large and its highlight the same, with the todo list centred in the column beside it. Tab lists are `ScrollView` + `LazyVStack`, not `List`: a macOS `List` ignores `contentMargins`, and capping its frame moves its scroller into the window.
- **Toolbars:** every tab is titled with its name (Todos too, whichever list is shown), then its actions in one order: filter (`ToolbarFilter`, or the PR tab's repo menu), add, then search, which macOS keeps at the trailing edge whatever the order asked for. Sync status and Sync Now live only in the sidebar's footer (`SidebarSyncFooter`): the oldest of the shown sources' last syncs, or which one is failing, with each source's error a click away. Tabs say only what setup step a source needs.
- **One style per kind of record** (`RecordStyle.swift`): each kind has one icon and colour, wherever it appears; calendar events take their record's. A record in a list is a `RecordRow`: icon, title over a secondary line, and on the right the date that list needs over a badge, with one row view per kind shared across lists. Search's secondary line is the match instead, and it groups results by kind. A PR's row says what it needs from me, coloured only when it needs me, else where it stands.
- **Sections:** every list section has one header (`SectionHeader`): title, a plain count, then `›` to open its tab or `+` to add. Lists on a tab of their own are unboxed, their headers pinned; lists embedded in a page or the Dashboard are boxed, the header above the box. A long list shows a page more at a time (`ShowMoreButton`), not all at once.
- **Opening a record:** a click selects; a double-click opens (`onRecordClick`), everywhere a record is listed: the tabs, the Dashboard, Search and detail pages. On a tab, Return opens too; the person page's arrows move through all its lists as one, Return opens and Escape closes a card (`PageKeyboard` takes it into the todo list). The Dashboard's panes and other detail pages' lists have no keyboard selection. A page takes focus back when a card closes (`DetailPage.focusRequest`), or its keys stop working, and leaves arrows and Return to a text field or editor that has the keyboard (`isEditingText`). A markdown editor in a card opened on a SwiftUI page takes focus itself (`focusOnAppear`): a `FocusState` request made as the card is created races the editor's creation and is sometimes lost. A card's `FocusState` is cleared when it closes, or reopening it sets the same value and nothing happens. A double-click opens only a row already selected, as a card collapsing above it between the clicks would move another row under the second. A record with notes (meeting, interview, person, project) opens as a page; a one-line record (todo, log entry, PR) expands in place on the shared card (`recordCard`). The double-click is read from the event's click count, so a single click selects at once rather than waiting to rule out a second. Every tab and page takes focus when it appears, its list or else itself, so arrow keys work at once and the sidebar's highlight is always the unfocused grey. A page that didn't would leave SwiftUI to hand focus to its title, text selected, where a keystroke replaces it.
- **Card controls** end every editable card in the same order, bottom right: the record's pills or picker icons, then the privacy eye (`PrivacyEye`). No trash on cards: delete is in the context menu, on the open card as on its row, and the Delete key on a selected row. Only permanent deletes confirm; a todo goes to the Trash at once.
- **Navigation:** `Navigator` opens a linked record with notes by pushing its page onto the current tab's stack, so Back returns to the link. A one-line record opens on its own tab instead, selected and expanded (`openTodo`, `openPullRequest`, `openLogEntry`); the PR tab expands a collapsed section or shows more rows to reach it. Lists on detail pages follow the same rule, except that a log entry opens on the Log, where its card lives. Switching tabs clears the stack. Links still open a tab hidden in Settings.
- **Commands and shortcuts** (`Commands/`): every app-level shortcut is an `AppCommand`, which drives the menus (`AppMenuCommands`) and the palette. The exceptions are the system's own Settings (Cmd-,) and Show Sidebar (`SidebarCommands`) menu items; the palette runs both too. An `AppCommand`'s `id` is stable: shortcut overrides (#70) will key on it. Views publish what they can do as `CommandHandlers` scene values, most specific first: the list last selected in (`selectionCommands`), the top page (`pageCommands`), the tab, then the app's (`CommandRunner`). A pushed page stays above its tab's lists and commands, which live on underneath it. Not by focus: `.focusedValue` never reached the menus from the lists, and a clicked list's focus state reads nil though its keys arrive. Keys a list handles itself (Return, Escape, arrows, Space, Delete, the calendar's T) stay `onKeyPress`, not menu items. New Todo and New Log Entry draft inline where the tab or page can, else open Quick Entry. Join Meeting (Cmd-J) and Open Meeting (Cmd-N) list all of today's meetings, or the next day's when today has none, and select the one under way, else the next, so the key and Return pick it without looking (`TodaysMeetings`). On a meeting or interview page, Cmd-J joins that one. Not Cmd-M: that's Minimize.
- **Menu keys come before the text view.** A Cmd-Delete typed in text would reach the Delete command, so `CommandHandlers.perform` hands it back to the text, and Delete stays enabled because a disabled menu key swallows its key with a beep. The markdown editor's own keys (Cmd-B, Cmd-I, Cmd-K for a link) still win, as `performKeyEquivalent` reaches the window's views first. AppKit's `isEnabled` on these menu items doesn't follow SwiftUI's state: test a command by pressing its key.
- **Focus a view that has just appeared on the next turn** (`DispatchQueue.main.async`), not in its `onAppear`. Asked for in the update that inserts it, before it's in the window, SwiftUI moves focus between it and the window a few times and can stop on the window: the palette opened deaf to keys, Escape included. `.defaultFocus` didn't move focus at all.
- **Hiding a tab** in Settings › Sidebar hides its Dashboard panes too.
- **Text fields bound to a model** go through `.skippingNoOps`. A `TextField` writes its current value back when it takes focus, and SwiftData counts that as a change. The app refreshes open records when the CLI writes (SwiftData's remote change), but not ones with unsaved changes, and saving one writes back every field as the app last read it, silently undoing the CLI's write. A field you really edit still wins over the CLI's write to that field, until the app saves.

## Rules by area

- **Projects and tags:** todos, log entries, meetings and PRs each take one project, set from the card (or a meeting's header) and the CLI's `--project`. Only log entries have tags: they say what kind of entry it is (`weekly-review`, `goals`), which the other records already are by their type. Don't file a recurring kind of entry as a project: projects complete, and an entry has only one.
- **A log entry's day** is picked on its card (`LogDatePopover`); the time of day stays, so the entry keeps its place among that day's. Quick Entry saves at the current time on the picked day.
- **Meetings** are made only from a calendar event's Add Notes; the calendar event owns the date and the attendees, which sync copies onto the meeting on every run. An event of 15 or more people leaves its meeting's attendees as they were. Deleting a meeting keeps its todos and event. Putting a recurring meeting into a project offers to put its series' other meetings in too, moving any in another project; only the user's yes does it (the CLI's `--series`). A series meeting's page lists the series' earlier events under a collapsed Previous Meetings, those without a meeting too (with Add Notes), since a missed week is history as well; hidden ones only if they have a meeting. A new meeting in a series starts in the project all its other meetings share, unless that project is completed; if they disagree, or any has none, it starts with none.
- **Interviews** come only from calendar sync, as stubs for events titled like an interview (`InterviewHeuristic`). They're private by default. Deleting one hides its calendar event, since sync would otherwise grow a new stub.
- **PR sync** (`GitHubSync`): repos are added and removed from the Pull Requests tab's toolbar menu (or its setup step, for the first), not in Settings, so a new user finds them where the PRs would be; `GitHubRepo.parse` takes a pasted link too. Adding one syncs at once. My PRs (`isMine`) are those I wrote (`isAuthoredByMe`) or am assigned to (`isAssignedToMe`, from schema V4: an agent's, opened for me), and are never review requests; a predicate spells out both flags. Only fetches asking for `assignees` (my open PRs, enrichment) can clear the assignment, which makes a PR I didn't write a teammate's. A PR is a review request (`isReviewRequest`) once requested, for good, even if a teammate fetch found it first. One only a teammate or reviewed-by-me fetch found is `isTeammateOnly`. Merged and closed fetches leave out `reviewDecision`, which times out.
- **Open PR details** (`GitHubEnrichment.swift`): the list fetches only discover PRs. Every PR open locally is then looked up by number, in batches of aliased GraphQL `pullRequest(number:)` lookups, for CI, mergeability, reviews and review requests; that also closes PRs no list returns any more. `gh pr list` can't ask which checks are required. `gh api graphql` exits non-zero when one lookup fails (a deleted PR) though the rest of the data is there, so it runs with `allowsNonZeroExit`.
  - CI (`CIRollup`) counts only required checks, so a flaky non-blocking test doesn't fail it: the latest run of each name, required by GitHub's `isRequired` or by the base branch's rulesets (`rules/branches/{base}`), which also catch required checks that haven't started. Classic branch protection needs admin to read, so on a repo using it only started checks count. Drafts skip the rulesets, as some required checks only start once a PR leaves draft. With nothing required (a PR stacked on another branch) it falls back to the overall rollup.
  - Reviews merge `latestReviews` (a comment after an approval hides it) with `latestOpinionatedReviews` (drops dismissed ones), and leave out bots. Only a summary is stored (`reviewStatus`, `myReviewIsOutdated`, `lastReviewedAt`), worked out at sync against the head commit; only staleness depends on the time.
  - `PullRequest.attention` turns this into what a PR needs from me (`PRAttention.swift`). Stale means no review for two working days since it asked.
- **Pull Requests tab:** open PRs in sections by `attention().section` (Needs You, Waiting on Others, Team in Flight), then this week's merged PRs, then every other merged or closed one under Older, each collapsed. The shared PR row, colour only on what needs me; its age is when the reason began (`PRAttention.since`), the last update for my PRs' own problems. An expanded card keeps the row as its first line, so nothing moves. The Dashboard's Review Requests and the menu bar's count are `needsMyReview`: a review requested, or a re-review. The Log lists my PRs only once merged (`Feed`), filed under the merge; one opens into a card for my notes and project, with GitHub a button away.
- **Calendar sync** (`CalendarSync`): timed events from the primary calendar; all-day events only from the allowlist; attendees linked only for events under 15 people. Every sync fetches the whole window (a week back to `calendarFetchWeeks` ahead), every page, and removes local events in it that Google didn't return. Google doesn't send a cancelled record for every deletion (an instance dropped from a recurring series, an interview pulled by the recruiting system), so absence is the only reliable signal: never go back to `updatedMin` or tombstones. A fetch cut short throws rather than reading as deletions. Declined events count as gone. An event moved out of the window is removed, and comes back as a new row when the window reaches it.
- **Outside invitations** (`isFromOutside`, `isAcceptedByMe`, from schema V6): sync marks an event on the primary calendar from outside when its organiser's email domain isn't the primary calendar's, judging an event on a shared calendar (`*.calendar.google.com`) by its creator instead, and an event with no organiser as outside. Other calendars are ones I added, so never. Only accepted counts as accepted; tentative doesn't. Events last synced before V6 read as inside, and older than sync's week back they stay that way. The CLI leaves these out (docs/cli.md); the app shows everything. While the setting's on, sync names a new attendee of an unaccepted one from their email, since the sender sets guests' display names. An event organised inside my domain renames anyone still named from their email, unless I added them (`GoogleCalendarAttendee.name`); an outside one never renames anyone. Spoofing an internal organiser through an emailed `.ics` isn't caught.
- **Declining and deleting events** (`CalendarWrite`, from an event's popover or right-click menu): timed events only, since all-day ones can come from calendars other than the primary. A sandbox offers them too: its events come from its own login (`.scratch`), and on a seeded one Google answers not found. A sandbox never syncs GitHub, in the app or the CLI: `gh` and the repos are the real ones, so it would pull in real PRs. Sync records whether I organise each timed event (`isOrganizedByMe`, from schema V3), so the menu offers Delete for mine and Decline for the rest. Events last synced before V3 read false, so each write still reads the event from Google first: delete only an event I organise, decline only one I'm invited to. A decline patches `attendees` with just my response and `attendeesOmitted`, since a patch's `attendees` replaces the whole list. Guests are told either way. The event is then dropped here, as the next sync would find it gone; Hide is the local-only way to remove one. A guest's delete isn't an error to Google: it declines and takes the event off that guest's calendar, as Google Calendar's Remove does.
- **Setup** (`SetupCheck`): each source is not installed (`gh` only), not logged in, missing its scope, unconfigured or ready, rechecked before every sync and whenever the app comes to the front. A source that isn't ready skips its sync instead of recording a failure; its tab and the Dashboard checklist say the next step. `gh` counts as logged in from `gh auth token`, which reads the stored token without the network, so being offline never reads as logged out. The calendar counts as logged in from the scopes saved in its keychain item's attributes (`GoogleKeychain`), which are readable without the token, so the check never prompts and needs no network. A failed Keychain read keeps the last state, and syncs if that was ready, so the failure shows as a sync error rather than a login prompt. Only a refresh Google answers with `invalid_grant` means logged out: `GoogleAuth` deletes the item, so the next check asks to log in. Any other failure, the network's included, says nothing about the login. Setup needs the full `calendar` scope, since the app declines and deletes events: a login with it unticked on Google's consent screen counts as missing its scope.
- **Calendar login** (`GoogleLogin`), only in a build that carries `GoogleClient.json`: the loopback flow with PKCE, and `prompt=consent` so a refresh token always comes back. It saves the client's ID and secret with the refresh token, so the CLI can refresh without the app's bundle. Only the app logs in. It names itself and the CLI in its own `Contents/Helpers` in the keychain item's access list (docs/security.md), and deletes and re-adds the item rather than updating it, so the list names the binaries installed now. A Debug app on the real store would replace the real item with one the installed app and CLI have to prompt for, so a sandbox logs in to an item of its own (`.scratch`), and its setup check reads only that one: a sandbox asks for a login until it has its own.
- **Setup checklist** (Dashboard): new users are guided in the app, not a doc. Backups join once there's a todo, log entry or meeting to lose. The roster step counts done once anyone has a Slack handle, or both an email and a GitHub handle (sync only ever fills one); the review step once a log entry is tagged `weekly-review`. Both can be skipped (`skippedSetupSteps`); backups can't.
- **Sync loops:** each source runs its own `Task.sleep` loop in the app. Failures record per source in `SyncHistory` (`captains-log status`); GitHub saves what worked and reports the rest.
- **History pruning:** SwiftData's persistent history can't be switched off and nothing reads it, so the app's hourly loop deletes transactions older than 14 days (`HistoryPruner`). Only the app prunes.
- **Retention** (`Retention.swift`, Settings › Retention): per kind, on by default, 30 to 365 days. A setting stored in UserDefaults wins over the default, so an install that switched a rule off keeps it off. The app's hourly loop runs it after the backup; `captains-log prune` lists, or with `--permanently` removes. Interviews go, with their calendar event (its title often names the candidate) and todos, counting from the later of the interview and its debrief, but only once no linked todo is open (completed or trashed counts as closed), so an unsubmitted scorecard keeps one. The calendar events rule also deletes meetings, written or not, by `date`; their todos stay, unlinked. Events with an interview are left to the interview rule. Calendar sync looks a week back, so deleted events don't return. `remove` deletes PRs first: `PullRequest.delete` fetches the todos it unlinks, and must not reach ones an interview deleted. PRs go by `lastActivity` (GitHub's `updatedAt`), linked or not, and sync skips PRs older than the same cutoff, so they don't come back. `Todo.pullRequest` has no inverse, so `PullRequest.delete` unlinks todos by hand.
- **Search** (`Searcher`) is one engine for the app and CLI: every word must start a word somewhere in the record, ignoring case and diacritics.
- **People** pages list meaningful contacts only (linked to more than a calendar event, or `isAddedManually`). Listing every unlinked person instead would bring back the GitHub-only authors and reviewers of PRs retention deleted. A roster import (`Roster`) matches by email, then GitHub, then Slack handle, only fills empty fields, and flags everyone it creates or updates, so a hidden calendar attendee it names is listed; that alone makes a row an update. Adding a person by hand (`Person.add`) is a one-row roster import, except that one matching two people is refused, since folding them is a merge, and a name alone will do. A name matches no one, so the sheet and the CLI warn about a namesake already listed. Every write path trims names, emails and handles (`Person.trimWhitespace`); the detail page binds keystroke by keystroke, so it trims on Return, focus loss and leaving the page (`onCommit`), never in the binding.
- **Who I am** is `Person.isSelf`, for Claude's sake: the app doesn't read it. It lives on the model rather than in settings so it survives a restore, a merge (`Person.absorb` carries it) and sandbox stores. `markAsSelf` keeps it to one person. Sync never sets it: `captains-log whoami` guesses from `isAuthoredByMe` PRs and calendar attendance, and the skill has Claude ask and run `whoami --set`.
- **Markdown editor** (`Views/Markdown/Native/`): a TextKit 1 `NSTextView` that restyles only the lines an edit touches (`MarkdownLineScanner`), and writes the model in bursts, before any click or command key.
- **Backups:** see `docs/security.md`. `age -p` only reads a terminal, so key creation runs it under `script(1)`; restore runs `age` through `runInteractiveProcess`, since `Process` puts children in a background process group that can't read the terminal.
- **Todos and projects:** `docs/todos.md`.
